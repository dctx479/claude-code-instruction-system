## 📋 详细方案对照

### 1. 上下文优化系统

#### 核心问题
- 原始数据（56KB截图、45KB日志）全量进上下文
- 过程数据挤占工作记忆
- compact后丢失上下文，需重新输入

#### 方案A：轻量级借鉴（推荐）✅
**实现**：
- 决策路由层：批量Read → 脚本聚合
- 结果摘要：大输出自动提取关键信息
- 记忆索引：SQLite FTS5快速检索

**优势**：
- 无额外依赖（Python标准库）
- 完全自主可控
- 符合"简单优先"

**投入**：2-3天

**详见**：`specs/SPEC-context-optimization.md`

#### 方案B：完整引入Context Mode（备选）
**能力**：
- 12种语言沙箱执行
- 双路检索（词干+trigram）+ RRF融合
- TTL缓存（24h）+ Levenshtein纠错

**劣势**：
- Elastic License 2.0（限制托管转售）
- 需要Node.js + 多语言runtime
- 黑盒服务，故障难排查
- 98%是营销数字，实际约60%

**风险**：RISK-HIGH（许可证冲突、外部依赖）

**详见**：`specs/SPEC-context-optimization.md` 方案B部分

---

### 2. 双系统决策与自进化

#### 核心问题
- 所有判断都调用大模型（7+秒）
- 同一任务执行100次仍可能犯第1次的错
- 每接入新环境需重新"教学"

#### 方案A：规则引擎+经验库（推荐）✅
**实现**：
```python
# 决策树
简单命令 → 直接执行（wc/grep/jq）
重复模式 → 查询Playbook
已知失败 → 返回已知方案
其他 → 调用大模型
```

**核心组件**：
1. **决策路由引擎**：规则匹配 + 相似度计算
2. **Playbook系统**：版本化流程 + 成功率追踪
3. **失败记忆**：错误模式 + 解决方案

**优势**：
- 轻量（Python标准库）
- 完全控制
- 可持续迭代

**投入**：3-5天

**详见**：`specs/SPEC-dual-system-decision.md`

#### 方案B：完整引入Agnes Harness（不推荐）
**能力**：
- Agnes Sys1.0（9B决策模型）
- TTT（测试时训练）
- RSI（递归自我改进）
- MHS（模型硬件标准）

**性能**：
- 决策速度快14.3倍
- 成本降至1/27
- 任务耗时减少32.9%

**劣势**：
- 9B模型需GPU（18GB内存+存储）
- 多组件故障风险高
- MHS对太一无用（非硬件项目）
- 迁移成本2-3周

**风险**：RISK-HIGH（资源开销、复杂度、过度设计）

**考虑时机**：
- 仅当太一需支持硬件设备（机器人、IoT）
- 决策延迟成为核心瓶颈（>50%任务）
- 有专职团队维护

**详见**：`specs/SPEC-dual-system-decision.md` 方案B部分

#### 方案C：混合方案（中期目标）
**分阶段实施**（6-12个月）：
1. C1: 自研1B决策模型（基于积累的500+决策日志）
2. C2: 借鉴RSI复盘机制（任务失败/耗时超预期时触发）
3. C3: 插件版本管理（v1.0 → v1.1 → latest指针）

**前提条件**：
- 方案A已运行3个月
- 识别出10+高频Playbook
- 有明确性能瓶颈

**详见**：`specs/SPEC-dual-system-decision.md` 方案C部分

### 3. 证据驱动验证系统

#### 核心问题
- 证据分散（commit/issue/memory/文档）
- 可信度不明（无法量化"多可靠"）
- 溯源困难（规则怎么来的？）
- 验证缺失（无相似度/准确度测量）

#### 方案A：增强memory系统（推荐）✅
**实现**：
```yaml
evidence:
  - id: ev-001
    type: test  # test|commit|measurement|observation|documentation
    source: "tests/test_backup.py:45-67"
    confidence: 0.95
    verified_by: human  # human|ci|tool|peer-review
    metrics:
      collision_rate_before: 1.0
      collision_rate_after: 0.0
```

**核心组件**：
1. **证据字段Schema**：标准化格式
2. **查询接口**：追溯证据链、按置信度筛选
3. **可视化命令**：`/evidence-trace`
4. **审计工具**：`audit-evidence.py`

**优势**：
- 增强现有系统（向后兼容）
- 零依赖（Python标准库）
- 轻量实现

**投入**：3-5天

**详见**：`specs/SPEC-evidence-driven-verification.md`

#### 方案B：引入Craft Anything（不推荐）
**能力**：
- 逆向引擎（反汇编/反编译/Ghidra）
- 证据台账（字节级追踪）
- 量化测量（相似度百分比）
- Clean room模式

**劣势**：
- 场景不匹配（太一是编排工具，非逆向工具）
- 300+工具严重违背"按需加载"
- Early alpha（v0.6.1不稳定）
- 99%任务不需要反汇编

**风险**：RISK-HIGH（过度工程化）

**详见**：`specs/SPEC-evidence-driven-verification.md` 方案B部分

#### 方案C：混合方案（长期考虑）
**选择性接入**（仅在特殊需求时）：
- 只接入verification工具（craft-compare/craft-measure）
- 排除逆向工具（disassemble/decompile/ghidra）
- 按需安装策略（发现二进制分析任务时提示）

**应用场景**：
- 分析二进制Hook安全性
- 验证自动生成代码与规格一致性

**详见**：`specs/SPEC-evidence-driven-verification.md` 方案C部分

#### 决策树
```

    ├─ Token消耗过高 → 评估Context Mode
    ├─ 决策延迟过高 → 训练轻量决策模型
```

## ⚠️ 风险提示

### 通用风险

#### R1: 过度工程化
**表现**：为了功能而功能，引入不必要的复杂度

**缓解**：
- 严格遵循"简单优先"原则
- 每个功能需有明确的业务场景
- 定期review是否有未使用的功能

#### R2: 维护负担
**表现**：规则库/Playbook/证据膨胀，难以管理

**缓解**：
- 定期清理（每季度）
- 删除命中率<1%的规则
- 合并相似规则/Playbook

#### R3: 外部依赖风险
**表现**：依赖项停止维护、API变更、许可证变化

**缓解**：
- 优先选择轻量方案（无外部依赖）
- 完整系统通过MCP松耦合
- 准备降级方案（外部服务故障时）

### 特定风险

#### Context Mode
- **许可证风险**：Elastic License 2.0可能冲突
- **黑盒风险**：故障难排查
- **缓解**：采用轻量方案，避免完整引入

#### Agnes Harness
- **资源风险**：9B模型需GPU（18GB）
- **复杂度风险**：多组件协调
- **缓解**：仅在明确瓶颈时考虑，优先自研1B模型

#### Craft Anything
- **场景不匹配**：太一很少需要逆向
- **Early alpha风险**：API不稳定
- **缓解**：长期储备，仅在特殊需求时考虑

## 🔄 迭代策略

### 敏捷原则
1. **小步快跑**：每个功能2-5天交付
2. **快速验证**：在真实场景测试，收集反馈
3. **持续迭代**：根据数据调整，而非主观猜测

### 决策原则
1. **证据驱动**：所有决策基于数据/测试/用户反馈
2. **简单优先**：能用规则解决就不用模型
3. **按需加载**：不因功能酷炫就盲目引入

### 停止信号
出现以下情况立即停止：
- 连续2周无实际收益
- 维护成本>节省收益
- 用户反馈负面（误判率高、干扰工作）
