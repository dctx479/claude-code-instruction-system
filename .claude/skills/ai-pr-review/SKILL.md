# AI-PR-Review — AI 时代的 PR Review 策略器

> 写代码越来越便宜，理解还是原来的价。本 Skill 不是教你怎么用 AI 写代码，而是解决"Agent 几分钟吐一千行，Review 跟不上了"这个新瓶颈。

## 它解决什么问题

| 痛点 | 来源 | 数据 |
|------|------|------|
| Agent 写代码按月涨速，人眼读速度不变 | Faros AI 2026 报告 | 任务吞吐 +34%，**零 Review 合并 +31%** |
| 代码 churn 暴增 | Faros AI | +861% |
| 中位 Review 时长 | Faros AI | **+442%** |
| 每个 PR 关联事故 | Faros AI | +243% |
| 开发者缺陷率 | Faros AI | 9% → 54% |
| 产出 4×，价值仅 +12% | GitClear | 中间 gap 几乎全是 Review + 返工 |
| AI 合著 PR 问题数 | CodeRabbit | 约人写 1.7× |

**根因**：把机器速度的输出，灌进了为人眼速度设计的流水线。瓶颈从"写"挪到了"验证"。

## 与现有 Skill 的边界（重要，避免重复）

| Skill | 视角 | 阶段 | 关系 |
|-------|------|------|------|
| `pr-prep` | 提交方 | 提 PR **前**的工程卫生 | 上游：先跑 pr-prep |
| `plan-review` | 评估方 | 实现**计划**的 10 维度 | 上游：复杂需求先用 plan-review |
| `spec-first` | 流程方 | 规范→开发→验收闭环 | 上游：业务需求先用 spec-first |
| **`ai-pr-review`（本）** | **Reviewer** | **PR 落地后怎么审** | **终点：策略 + 分层 + 协议** |

四者关系：`spec-first` / `plan-review` → `pr-prep` → **`ai-pr-review`**

## What（输入/输出）

**输入**：
- 一个待 Review 的 PR（diff 范围、PR 描述、关联 Spec/Plan）
- 改动落点（模块 / 路径 / 风险分层）
- 可选：上一轮 Review finding

**输出**：
- **风险分层判定**（P0 核心 / P1 业务 / P2 样板）
- **5 条规则逐项 checklist**（每项 ✅/⚠️/❌ + 证据）
- **Review 行动建议**（建议合 / 建议改 / 阻塞 + 理由）
- **审计轨迹**（分诊 / 抽检 / 验收 三阶段记录）

## When Done（验收标准）

- [ ] 风险分层已明确（P0/P1/P2）
- [ ] 5 条 Review 规则逐项已检
- [ ] 分诊 / 抽检 / 审计三阶段已留痕
- [ ] 合并按钮的最终责任人已显式声明
- [ ] 未验证项已显式声明（不靠"测试过了"推断）
- [ ] QA Evidence 已包含 Done / Unverified / Blocked 三段

## What NOT（边界约束）

- ❌ **不替你做业务判断**——"该不该做"是产品决策，AI 给不了
- ❌ **不自动合并**——合并按钮永远属于人类（详见规则 5）
- ❌ **不复制 AI Reviewer 输出当结论**——AI Review 是传感器，不是判决
- ❌ **不评审实现计划本身**——那是 `plan-review` 的活
- ❌ **不替代代码风格审查**——那是 `code-reviewer` 的活，本 Skill 只给策略层

## 核心方法论：按风险分层（先便宜后昂贵）

> 1 个 P0 改动需要的 Review 工时 ≈ 10 个 P1 ≈ 100 个 P2。错配 = 浪费或事故。

### 风险三档

| 档位 | 典型场景 | 必做 Review | 选做 Review |
|------|---------|-----------|-----------|
| 🔴 **P0 核心交易路径** | 支付/扣款/鉴权/订单状态机/分布式事务 | 类型检查 + 单测 + 2 个不同 AI Reviewer + 人类 Owner + 安全扫 + Spec 对齐 | 性能压测、Mutation Testing |
| 🟡 **P1 通用业务逻辑** | 业务规则、API、CRUD、报表 | 类型检查 + 单测 + 1 个 AI Reviewer + 抽检 | 业务边界 case |
| 🟢 **P2 样板/UI/文案** | 样式、注释、纯文本、配置 | Linter + 1 个 AI Reviewer 扫一眼 | 无 |

**反模式（禁止）**：
- ❌ 在 P2 上重型 Review（浪费）
- ❌ 因为测试绿了就让 P0 改动溜走（事故生成器）
- ❌ 所有 PR 一视同仁（远低于最佳投入产出比）

### 5 条 Review 规则（每条都给具体动作）

#### 规则 1：按风险分层，不按作者分层

**触发条件**：所有 PR 默认必须分层。
**落地动作**：
- PR 描述必须**显式标注风险档位**（P0/P1/P2）——不标视为 P1
- Linter 配置按档位动态启用（P0 启用 strict + 安全规则集）
- Review 工具调用次数按档位配置（P0 ≥ 2 个 AI Reviewer，P1 ≥ 1 个）

**失败模式**：见 §六.五 Karpathy 规则 2「简单优先」——加 1 个检查就够的，不要加 10 个。

#### 规则 2：提 PR 前先交证据（拒绝三无改动）

**触发条件**：所有 PR 提交前。
**禁止的「三无」**：
- ❌ 无改动目的
- ❌ 无可读 diff（>500 行无注释 / 3500 行无分段）
- ❌ 无测试输出 / 无证明跑过

**落地动作**：
- 提交方必须自填：变更目的 + 关键决策日志（"为什么用 X 不用 Y"）+ 测试命令 + 输出截图
- 缺失任意一项 → 自动标 🔴 阻塞，无需 Reviewer 进一步判断
- **意图重建的成本推回提交方，别全靠 Reviewer 扛**

**依据**：人写代码意图在脑子里，Agent 写代码意图在推理链里——但 diff 生成完，推理通常就扔了。PR 上不附「我为什么这么改、排除了什么」，Reviewer 就成了「第一个真正看过这段代码的人」。

#### 规则 3：故意保持 PR 小

**依据**：Faros 数据：Agent PR 平均比人写大 51%。大块读不完的 diff 要么被拒，要么被橡皮图章式通过。

**落地动作**：
- 默认单 PR ≤ 400 行（含测试）；超出必须拆分，**设计约束，不是礼貌**
- 给 Agent 下指令时显式写："小步提交，每步可独立 review"
- 拆分标准：**每一段 commit/PR 对应一个独立意图**（不是按行数机械切）
- 拆分优先于合并：宁可 5 个 200 行 PR，不要 1 个 1000 行 PR

#### 规则 4：测试改动比业务代码更仔细读

**Agent 经典翻车**：改坏行为 → 改断言让测试变绿。两百个测试全绿 ≠ 敢说改对了。

**落地动作**：
- 任何 PR 中**测试代码变更行数占比 > 40%** → 自动标 🟡 警告
- 测试改动必须回答三个问题：
  1. 这个断言抓的是**真实业务不变式**还是**实现细节**？
  2. 如果我把业务代码改坏，测试还能不能抓到？（→ 考虑 mutation testing）
  3. 这个新断言是不是「为这个 PR 通过而量身定制」的？
- 选做：在 P0 路径跑 mutation testing（Stryker / mutmut / PIT），值回票价

#### 规则 5：合并按钮必须有人类负责（不可外包）

**铁律**：AI Review 是传感器，不是判决。模型不能被值班叫醒，也不能为上线背锅。

**落地动作**：
- **谁点合并，谁拥有它**——显式写进 PR 模板的"Owner"字段
- AI Reviewer 输出"looks good"是**信号**，不是**许可**——平静自信的语气不等于挣到信任
- 合并后 24h 内如果出事故，第一问的不是"AI 怎么没抓到"，而是"Owner 为什么没看到"
- 禁止用"AI 都说好了"作为合并理由

## Human-on-the-loop 协议（Review 端到端）

> "人读每一行"那套结束了。但"写、审、判全是一家模型闭环自嗨"会一起漏——必须显式分层。

### 三阶段（按 PR 流入顺序）

```
incoming PR 队列
  ↓
[1] 分诊（Triage）—— Agent 跑首轮分类
  ↓
[2] 抽检（Selective Review）—— 人类按风险分层深读
  ↓
[3] 审计（Audit）—— 合并后系统级回归监控
```

#### 阶段 1：分诊（Triage）—— Agent 自动化

- **角色**：AI Reviewer + 静态分析
- **输入**：PR diff + PR 描述 + 风险档位自标
- **输出**：三档分类
  - 🟢 **可快合**：P2 样板 / 改动 < 50 行 / 风险档位自标准确 / 单测绿
  - 🟡 **需人读**：P1 业务 / 改动 50-400 行 / 涉及多文件
  - 🔴 **必深读**：P0 核心 / 改动 > 400 行 / 涉及安全/支付/数据
- **边界**：分诊结果**只用于分配注意力**，不替代合并决策

#### 阶段 2：抽检（Selective Review）—— 人类按档位介入

| 档位 | 人类投入 | 时长上限 | 关注点 |
|------|---------|---------|--------|
| 🟢 P2 | 扫一眼 PR 描述 + CI 状态 | ≤ 2 min | 风险档位自标是否准确 |
| 🟡 P1 | 抽检 30-50% 关键变更 | 15-30 min | 业务规则边界、Spec 对齐 |
| 🔴 P0 | 逐段读 + 2 个不同 AI Reviewer 结论交叉验证 | 1-4 h | 5 条规则全部过一遍 |

**反模式**：
- ❌ 人类对 P2 投入深读时间（浪费）
- ❌ 人类对 P0 只看测试覆盖率（事故生成器）
- ❌ 同一档位所有 PR 都按最高标准（不现实）

#### 阶段 3：审计（Audit）—— 系统级回归

- **角色**：CI / 监控 / 灰度
- **动作**：
  - 合并后 0-24h：核心指标监控（错误率 / 延迟 / 业务核心 KPI）
  - 异常自动回滚 + 通知 Owner
  - **审计日志必须可追溯**：每条合并都关联 Owner + 分诊结果 + 抽检记录
- **判据**：谁点合并，谁响应 24h 内的 P0 告警

### 极端案例参考（不照抄）

- **Kun Chen（前 Meta L8）**：日均 40 PR，基本不逐行 Review，但三件套兜底：
  1. 意图写进超长 Plan
  2. Agent 跑几小时
  3. 「No Mistakes」自动门禁
- **照搬警告**：把他的 solo + 高质量 Plan + 可控爆炸半径的方案套到 10 人支付团队 = 复现 Faros 曲线

## 8 条 Agent 时代 Review 反模式（黑名单）

| # | 反模式 | 后果 | 检测 |
|---|--------|------|------|
| 1 | 所有 PR 一视同仁 | 低优 PR 浪费 / 高优 PR 漏审 | 查分诊日志 |
| 2 | 让 AI 决定合并 | 模型不能被叫醒 | 查合并权限配置 |
| 3 | 测试绿 = 敢合 | Agent 改断言让测试变绿 | 测试代码占比 > 40% 警告 |
| 4 | 大 PR 一把提 | 没人读完，橡皮图章 | 行数硬限 |
| 5 | Reviewer 不分专业 | 全栈 Owner 抓不到细节 | 按模块指派 Owner |
| 6 | AI Review 100% 信 | 平静自信 ≠ 正确 | 抽检必做 |
| 7 | 合并后无审计 | 24h 事故无人响应 | 强制 Owner 字段 |
| 8 | 拒绝审查「样板 PR」 | 把责任推给提交方 | P2 也要标档位 |

## 与 pr-prep 的协作链

```
[pr-prep] 提 PR 前五步检查
    ↓ 输出：CI 绿 + 测试通过 + 描述完整 + commit 规范
[ai-pr-review] 本 Skill
    ↓ 输入：合规 PR + diff
    ↓ 输出：风险分层 + 5 条规则 + 分诊/抽检/审计
合并
    ↓
[code-reviewer] 深度代码风格审查（可选，P0 必选）
```

**关键差异**：
- `pr-prep` 解决"能不能提"（提交方视角，工程卫生）
- `ai-pr-review` 解决"该不该合"（Reviewer 视角，策略 + 协议）

## 与 SDD-RIPER 的集成点

| RIPER 阶段 | 本 Skill 介入 |
|-----------|--------------|
| R (Research) | 配合 plan-review 提供 Review 风险预估 |
| I (Innovate) | 不介入 |
| P (Plan) | 计划阶段就标好"哪些改动将落入 P0/P1/P2" |
| E (Execute) | 提交 PR 时按本 Skill 跑 pr-prep + 本 Skill |
| R (Review) | **本 Skill 主战场** |

**与 SDD-RIPER 五阶段的关系**：
- `sdd-riper-light` / `sdd-riper` 产出代码 + PR
- `pr-prep` 跑工程卫生
- `ai-pr-review` 跑策略 + 分层 + 协议（本 Skill）
- `spec-first` 跑规范对齐（若走规范驱动开发）

## 快速使用示例

### 场景 1：Agent 提了个 800 行的 PR

```
User: /ai-pr-review

Skill 输出:
  风险分层：🟡 P1（用户说"提了 PR"但没说档位，按 P1 默认）
  5 条规则:
    规则 1 [PASS] 但档位自标缺失 → ⚠️ 提示补
    规则 2 [PASS] 描述完整 + 测试输出已贴
    规则 3 [FAIL] 800 行 > 400 行上限 → 🔴 阻塞，请拆 PR
    规则 4 [PASS] 测试代码占比 18%
    规则 5 [PASS] Owner 字段已填
  分诊：🟡 需人读
  抽检建议：15-30 min，关注业务规则边界
  审计：合并后 24h 监控核心指标
  结论：🔴 阻塞（先拆 PR 再合）
```

### 场景 2：30 行的文案/PR 模板修改

```
User: /ai-pr-review

Skill 输出:
  风险分层：🟢 P2（提交方自标）
  5 条规则: 全部 PASS
  分诊：🟢 可快合
  抽检建议：≤ 2 min
  审计：常规
  结论：🟢 可合
```

### 场景 3：支付路径的扣款逻辑修改

```
User: /ai-pr-review

Skill 输出:
  风险分层：🔴 P0（命中核心交易路径）
  5 条规则:
    规则 1 [PASS] 档位自标 P0
    规则 2 [WARN] 缺"为什么不用乐观锁"的决策日志 → ⚠️ 补
    规则 3 [PASS] 380 行 < 400
    规则 4 [WARN] 测试占比 25% 但缺并发竞争用例 → 🟡 建议补
    规则 5 [PASS] Owner 已填
  分诊：🔴 必深读
  抽检建议：1-4 h，逐段读 + 2 个 AI Reviewer 交叉验证
  审计：合并后 24h 强监控 + 灰度
  结论：🟡 需补证据后深读
```

> 任何流程静悄悄崩掉前都有迹可循。以下指标月度看：

| 指标 | 红色阈值 | 来源 |
|------|---------|------|
| 零 Review 合并率 | > 20% | Faros 报告 |
