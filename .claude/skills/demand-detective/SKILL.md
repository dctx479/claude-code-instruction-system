# Demand Detective — 业务需求前置澄清器

> 需求不是写出来的，是问出来的。本 Skill 不替你写 PRD，而是在写 PRD 之前，把那些模糊的、一句话的、靠感觉讲出来的需求，拆成可以确认的业务决策。

## 它解决什么问题

| 痛点 | 典型表现 | 后果 |
|------|---------|------|
| **一句话需求** | "能不能做一个样衣借出功能？" | 直接做 → 上线后发现规则没说清 |
| **业务方不会描述方案** | 问他"你想怎么借"答不上来 | 需求停在表面 |
| **直接给方案** | 文档漂亮但核心规则没确认 | 错的流程被系统固化 |
| **临时拍脑袋的字段** | 字段填了但语义不清 | 后期返工 |

**铁律**：错的流程被系统固化，比没有流程更糟。

## 与现有 Skill 的边界（重要）

| Skill | 层 | 阶段 | 关系 |
|-------|-----|------|------|
| `vision-builder` | 愿景层 | 模糊需求 → VISION.md | **上游**：先有愿景 |
| **`demand-detective`（本）** | **业务决策层** | **一句话需求 → 业务决策清单 + 分级任务单** | **本层** |
| `spec-writer` (Agent) | 规范层 | 业务决策 → SPEC-*.md | **下游**：决策确定后写规范 |
| `spec-first` | 流程层 | spec-writer → 开发 → qa 闭环 | **下游**：SPEC 完成后接流程 |
| `plan-review` | 评估层 | 评估计划文档 | **并列**：本 Skill 输出物可作为输入 |

关系链：`vision-builder` → **`demand-detective`** → `spec-writer` → `spec-first` → `plan-review` → `pr-prep` → `ai-pr-review`

## What（输入/输出）

**输入**：
- 一句话或一段模糊需求（必需）
- 业务背景（可选：行业/角色/已有系统）
- 已知约束（可选：时间/预算/合规）

**输出**：
- **场景反讲段**（用业务语言复述一遍）
- **业务决策清单**（A/B 选择题 + 代价说明）
- **分级开发任务单**：
  - **核心确定区**（已确认，必须严格实现）
  - **假设验证区**（不确定，按默认方案做 + 标为可配置）

## When Done（验收标准）

- [ ] 已输出场景反讲段（含角色、场景、动作、目标、风险）
- [ ] 业务决策清单已覆盖：业务边界、流程规则、字段校验、体验优化 4 层
- [ ] 每个 A/B 题都给了"好处 / 代价"两面
- [ ] 输出物分成了核心确定区 + 假设验证区
- [ ] 假设验证区的每条都标了"如何后续调整"（配置项 / 规则引擎 / 状态字段）
- [ ] 用户已确认核心确定区

## What NOT（边界约束）

- ❌ **不写 PRD / SPEC**——那是 spec-writer 的活
- ❌ **不替业务方做业务决策**——只把决策摆出来
- ❌ **不讨论按钮放左放右**——体验细节不是本层的事
- ❌ **不评估技术方案**——那是 plan-review / architect 的活
- ❌ **不解决跨需求依赖**——只澄清单条需求的内部决策

## 核心方法论：少问开放问题，多给 A/B 决策题

### 为什么不要直接问"你想怎么做"

业务方脑子里没有产品模型。问他"你想怎么借"——他答不上来。

更好的方式：把两种典型方案摆出来，把利弊讲清楚，他反而容易判断：
- "对，我们公司就该这样。"
- "不对，我们业务员经常要临时拿样，不能这样。"

**核心公式**：`A 方案（好处 / 代价）` + `B 方案（好处 / 代价）` + 一句"在你公司是哪种？"

## How（3 步执行流程）

### Step 1：反讲场景

> 不急着写方案，先用自己的话把业务故事复述一遍。

**模板**：

```markdown
**场景反讲**

假设有一位 [角色]，在 [触发场景] 时，需要 [动作]。
他最关心的是 [业务目标 A]，同时公司又希望 [业务目标 B]，避免 [业务风险 C]。

关键约束：
- [已知约束 1]
- [已知约束 2]
```

**反讲要素清单**（5 个一个都不能少）：
| 要素 | 含义 | 错误示例 |
|------|------|---------|
| **角色** | 谁在做事 | 缺 → "系统应该支持借出" |
| **场景** | 在什么情境下 | 缺 → 同样需求在仓库/门店/线上完全不一样 |
| **动作** | 具体做什么 | 缺 → 借出 vs 调拨 vs 试穿完全是不同流程 |
| **目标** | 业务想达成什么 | 缺 → 没目标就不知道什么叫"做对" |
| **风险** | 不做 / 做错会怎样 | 缺 → 没法评估方案代价 |

**验证**：把反讲段给业务方看，他能不能不假思索地说"对，就是这样"？不能就回到 Step 1。

### Step 2：把不确定的地方变成决策题（按影响范围从大到小）

**4 层问题漏斗**（不要跳过层）：

```
第 1 层：业务边界（影响最大，不问清后面全跑偏）
  ↓
第 2 层：流程规则（业务流程的核心决策点）
  ↓
第 3 层：字段校验（具体数据怎么填、怎么查）
  ↓
第 4 层：体验优化（按钮放哪、提醒怎么发）
```

**为什么这个顺序**：很多需求讨论最大问题是一上来就陷入细节。半小时讨论按钮位置，但"系统到底要不要支持跨公司借样"没人确认——很危险。

**每层的问题模板**：

#### 第 1 层：业务边界

> 问的是"边界在哪里"，决定系统的归属/隔离规则。

**典型问题**：
- 这个系统服务总部统一管理，还是各子公司各自管理？
- 数据是全公司共享，还是按区域隔离？
- 资产是统一调拨，还是各地仓库自己管理？
- 是否要支持跨 X 借 / 调 / 看？

#### 第 2 层：流程规则

> 问的是"流程怎么走"，决定状态机和审批节点。

**典型问题**：
- 借出要不要审批？A. 必须审批 / B. 直接扫码借出
- 归还要不要质检？A. 强制质检才能入库 / B. 抽样质检
- 逾期怎么处理？A. 每天提醒直到归还 / B. 三天未还自动上报主管
- 丢失损坏怎么追责？A. 责任人原价赔偿 / B. 按折旧价 / C. 保险兜底
- 状态变化会不会影响其他模块？（如库存、报表、权限）

**A/B 答案模板**：

```markdown
**Q：样衣借出要不要审批？**

**A. 必须审批后才能出库**
- 好处：责任清晰，库存安全，适合样衣价值高、跨部门借用多的公司
- 代价：流程会变慢，业务员临时拿样不够灵活

**B. 业务员可以直接扫码借出**
- 好处：快，推广效率高
- 代价：容易出现样衣丢失、逾期不还、责任不清的问题
```

#### 第 3 层：字段校验

> 问的是"数据怎么填"，决定表单的必填/选填/校验规则。

**典型问题**：
- 借出时客户是否必填？
- 预计归还日期是否必填？
- 数量上限 / 单次借出上限？
- 是否要扫码录入？（硬件约束）
- 是否允许批量借出？

**答案模板**：

```markdown
**Q：借出时客户信息是否必填？**

A. 必填（姓名 + 电话）
B. 选填（不填也能借出，但事后要补录）
C. 二选一（客户 / 内部领用，必填其一）
```

#### 第 4 层：体验优化

> 问的是"怎么用得爽"，决定 UI/通知/报表的形态。

**典型问题**：
- 要不要逾期提醒？提前几天？谁接收？
- 报表看什么维度？样衣周转率？款式推广次数？
- 要不要热门款式排行？
- 移动端 / PC 端优先级？

**警告**：第 4 层不该主导决策。如果业务方一上来就讨论"提醒怎么发"——拉回第 1 层。

### Step 3：输出分级开发任务单

**两块分区**（不是"全都要做"或"全都不做"）：

#### A. 核心确定区（已确认，必须严格实现）

格式：
```markdown
- [ ] [业务规则 1] — [来源：决策题 Q1 选项 A]
- [ ] [业务规则 2] — [来源：决策题 Q3 选项 B]
- [ ] [字段约束 X] — [来源：决策题 Q5 选项 A]
```

每个任务必须能溯源到一条决策题 + 一个明确选项。

#### B. 假设验证区（不确定，按默认方案做 + 必须可配置）

格式：
```markdown
- [ ] [假设 1] — 默认：[默认方案] / 配置项：[如何后续调整]
- [ ] [假设 2] — 默认：[默认方案] / 配置项：[如何后续调整]
```

**为什么必须有"如何后续调整"**：
- 真实世界很多需求不可能一开始就完全确定
- 不能因为不确定就不做
- 不能假装它已经确定了
- 正确做法：承认它是假设，把它设计成可调整

**示例**：

```markdown
- [ ] 逾期提醒规则 — 默认：提前 1 天 / 逾期当天 / 逾期 3 天通知主管
  配置项：规则引擎（msg_template_id + trigger_days）
  → 后续业务方想改成"提前 2 天 / 逾期 1 天通知业务员"时，不用改代码
```

### Step 4：理解确认摘要（闭环验证）

> 目标：**让用户知道 AI 已完全理解了需求**，而不只是记录了一堆问答。

在 Step 3 完成后，用一段简洁的"复述+确认"收尾：

```markdown
## 理解确认摘要

**我理解你要做的是**：
{用业务语言复述核心目标，1-2 句}

**已确认的关键决策**：
- {决策 1}：选择了 [选项]（来源：Q{N}）
- {决策 2}：选择了 [选项]（来源：Q{N}）

**我将假设的部分**（如有）：
- {假设 1}：暂定 [默认方案]，后续可调整

**如果以上理解有偏差，现在是最佳纠正时机。确认后我们进入规范编写。**
```

**为什么需要这一步**：
- Step 1-3 完成了"帮 AI 理解需求"，Step 4 完成了"让用户验证 AI 理解对了"
- 避免"我以为你明白了"的假闭环——用户点头不等于 AI 理解正确
- 为下游 spec-writer 提供一份经用户确认的事实基础

**快速通过规则**：如果 Step 3 输出时用户已明确表示"就这样做"，可跳过摘要，直接进入 spec-writer。

## 反模式黑名单

| # | 反模式 | 后果 |
|---|--------|------|
| 1 | 一上来就给方案 | 错的流程被系统固化 |
| 2 | 让业务方"自己想怎么搞" | 业务方不会描述方案 |
| 3 | 跳过业务边界直接聊流程 | 流程再对也跑偏 |
| 4 | 把"提醒怎么发"当核心决策 | 体验优化压过业务规则 |
| 5 | 决策题只给一个选项 | 强制业务方走预设路径 |
| 6 | 输出"全要做"或"全不做" | 真实需求几乎都有混合区 |
| 7 | 假设不标"如何后续调整" | 后期改不动 |
| 8 | 反讲段没问业务方确认 | 你自己脑补的场景不代表他 |
| 9 | 把所有字段都标"必填" | 业务流程死板 |
| 10 | 跨需求一起澄清 | 单条需求都说不清就别想着合并 |

## 与 spec-writer 的衔接规范

| 输出物 | 下游 | 衔接方式 |
|-------|------|---------|
| 场景反讲段 | spec-writer | 作为"功能描述"段的输入 |
| 业务决策清单 + 选项 | spec-writer | 作为"功能验收标准"的依据 |
| 核心确定区 | spec-writer | 直接转为"功能验收清单" |
| 假设验证区 | spec-writer | 转为"待确认事项" + "可配置项" |

**反模式**：
- ❌ spec-writer 跳过本 Skill 直接写 SPEC → 容易写出"漂亮但规则没说清"的规范
- ❌ demand-detective 输出物不喂给 spec-writer → 决策清单沦为一次性文档

## 适用与不适用

### ✅ 适用场景

- ERP / CRM / PLM / 进销存 / 审批流 / 报表系统 等业务逻辑重的系统
- 业务方说"能不能加个 X ？"且 X 涉及流程/规则/审批
- AI 时代的"一句话需求"（来自 PRD agent 自动生成的输入）
- spec-writer 阶段发现规则没说清需要回溯

### ❌ 不适用场景

- 纯 UI 体验优化（无业务规则决策）
- 技术架构问题（用 architect）
- 已有清晰 SPEC 的迭代开发（直接进开发）
- 单一明确动作的小需求（如"加个日志"）——直接做

## 快速使用示例

### 示例 1：样衣借出功能（原文案例）

**输入**："能不能做一个样衣借出功能？"

**Step 1：反讲场景**
> 假设有一位业务员，在客户临时要看样的时候，需要快速找到并借出某件样衣。他最关心的是样衣能不能及时拿到，同时公司又希望这个过程有记录，避免丢失和责任不清。

**Step 2：决策题清单（节选）**

| # | 层级 | 决策题 | 选项 |
|---|------|--------|------|
| Q1 | 业务边界 | 样衣是否允许跨门店借？ | A. 允许 / B. 仅限本门店 |
| Q2 | 业务边界 | 总部 vs 门店谁有最终审批权？ | A. 总部统管 / B. 门店自治 |
| Q3 | 流程规则 | 借出要不要审批？ | A. 必须审批 / B. 直接扫码借 |
| Q4 | 流程规则 | 归还要不要质检？ | A. 强制 / B. 抽样 |
| Q5 | 流程规则 | 逾期如何处理？ | A. 自动提醒 / B. 升级主管 / C. 两者都要 |
| Q6 | 字段校验 | 借出时客户信息必填吗？ | A. 必填 / B. 选填 / C. 二选一 |
| Q7 | 体验优化 | 逾期提醒提前几天？ | A. 1 天 / B. 3 天 / C. 可配置 |

**Step 3：分级任务单**

```markdown
## 核心确定区（待业务方选完后补全）
- [ ] 跨门店策略 — 来源：Q1 待选
- [ ] 审批流程 — 来源：Q3 待选
- [ ] 质检策略 — 来源：Q4 待选

## 假设验证区（先按默认做 + 可配置）
- [ ] 逾期提醒规则 — 默认：提前 1 天 / 逾期当天 / 逾期 3 天通知主管
  配置项：reminder_rules 表（trigger_days + notify_role）
- [ ] 客户信息是否必填 — 默认：选填（事后补录）
  配置项：borrow_form.required_fields JSON
- [ ] 报表维度 — 默认：周转率 + 推广次数
  配置项：report_default_metrics JSON
```

### 示例 2：报表需求

**输入**："我们想要一个报表，可以看到业务情况。"

**Step 1：反讲场景**
> 假设有一位业务主管，在月度复盘会上，需要看到整个团队过去一个月的关键指标，包括销售额、新客户数、跟进转化率。他最关心的是趋势是否健康，异常点在哪里。

**Step 2：决策题清单（节选）**

| # | 决策题 | 选项 |
|---|--------|------|
| Q1 | 报表服务谁？ | A. 仅业务主管 / B. 全员可见 / C. 分级可见 |
| Q2 | 时间维度？ | A. 仅月度 / B. 月+周+日 / C. 可切换 |
| Q3 | 异常如何告警？ | A. 仅显示 / B. 邮件 / C. 站内信 |
| Q4 | 是否要下钻到明细？ | A. 不下钻 / B. 下钻到客户 / C. 下钻到订单 |

## 健康度自检（流程层）

| 指标 | 红色阈值 | 来源 |
|------|---------|------|
| 决策题平均 A/B 选项数 | < 2 | 自定义（强制对比） |
| 业务边界层问题占比 | < 20% | 自定义（拉回第 1 层） |
| 假设验证区无"可配置"标注 | > 30% | 自定义（避免硬编码） |
| 场景反讲段未确认就进入 Step 2 | > 10% | 自定义（脑补风险） |
| 决策题累计选项数 < 3 的占比 | > 30% | 自定义（开放问题占比过高） |
