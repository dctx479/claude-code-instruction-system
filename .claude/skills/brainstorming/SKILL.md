# Brainstorming — PM 探索性思考伙伴

> 你的任务不是生成交付物，而是与 PM 一起思考。要有明确判断，敢于提出质疑，带来一些意料之外的视角，帮助对方想到那些一个人未必能顺着想到的点子。

## 它解决什么问题

| 痛点 | 典型表现 | 后果 |
|------|---------|------|
| **过早收敛** | 抓住第一个还不错的想法就停 | 错失更好的方案 |
| **先想方案后补问题** | PM 还没定义问题就先想"做 X" | 解错问题 |
| **功能对标** | "竞品有 X，所以我们也要 X" | 复制而非创新 |
| **分析瘫痪** | 探索很多但不收敛 | 议而不决 |
| **约束太早生效** | "技术做不了"压过发散 | 探索空间被砍 |
| **单一想法式脑暴** | 带着预设方案"走过场" | 决策没真正打开 |

## 与现有 Skill 的边界（重要）

| Skill | 角色 | 阶段 | 关系 |
|-------|------|------|------|
| **`brainstorming`（本）** | **发散探索 + 思考伙伴** | **问题空间/方案空间/假设验证/策略** | **本层** |
| `demand-detective` | 业务决策清单 | 一句话需求 → A/B 选择题 | **下游**：脑暴收敛后用 demand-detective 挖决策 |
| `vision-builder` | 愿景文档 | 模糊 → VISION.md | **下游**：脑暴收敛后用 vision-builder 输出愿景 |
| `hv-analysis-enhanced` | 横纵分析多视角 | 多视角决策 | **并列**：用 HV 替代或补充脑暴 |
| `plan-review` | 计划评估 | 计划文档评估 | **下游**：脑暴收敛出方向后写 Plan，再 plan-review |
| `spec-writer` | 规范文档 | Plan → SPEC | **下游**：脑暴 → Plan → SPEC |

关系链：**`brainstorming`（发散）** → `demand-detective`（挖决策）/ `vision-builder`（写愿景） → `plan-review`（评计划） → `spec-writer`（写规范）

## What（输入/输出）

**输入**：
- 一个产品想法 / 问题领域 / 战略问题（必需）
- 已知背景：用户研究、数据、约束（可选）
- 当前阶段：早期探索 / 方案评估 / 假设验证 / 策略制定（必需，缺则用 §0 模式判定）

**输出**：
- **结构化对话记录**（4 模式之一主导）
- **2-3 个可继续追的想法**（带最大未知项 + 最低成本验证方式）
- **明确搁置的内容**（有兴趣但不适合现在做的）
- **下一步建议**（研究 / 原型 / 访谈 / 写一页纸说明）

## When Done（验收标准）

- [ ] 已识别当前对话模式（4 模式之一）
- [ ] 用了至少 1 个框架（HMW / JTBD / SCAMPER / OODA）
- [ ] 发散环节至少 5-7 个方案（4 模式中"方案发散"强制）
- [ ] 至少做了 1 次反向思考（"怎么做会更糟" 或 "如果反过来呢"）
- [ ] 收敛到 2-3 个值得继续追的想法
- [ ] 每个想法标了最大未知项 + 最低成本验证方式
- [ ] 明确搁置的内容已记录
- [ ] 下一步建议已给

## What NOT（边界约束）

- ❌ **不生成交付物**——头脑风暴是对话，不是 PRD / 规范
- ❌ **不替 PM 做决策**——只生成选项，决策在后面结合更多数据
- ❌ **不生硬堆框架**——只在框架确实能帮助思考时才用
- ❌ **不锚定第一个想法**——PM 一开始就带方案进来时，先承认它，再追问
- ❌ **不把脑暴和决策混为一谈**——本 Skill 负责选项，决策权在 PM

## §0 模式判定（开始前必做）

| 触发信号 | 模式 | 目标 |
|---------|------|------|
| PM 知道有问题但没定义清楚是什么 | **问题探索** | 跳进方案前深入理解问题空间 |
| 问题清楚，需要生成多个可能方案 | **方案发散** | 先求数量再求质量 |
| 已有方向/想法，要先检验是否站得住 | **假设验证** | 投入执行前找最脆弱环节 |
| 思考的是方向、定位、大下注 | **策略探索** | 把战略空间看清楚 |

**判定流程**：

```
PM 问的是"该做什么吗？"          → 问题探索
PM 问的是"能做什么？"            → 方案发散
PM 问的是"这样做对吗？"          → 假设验证
PM 问的是"我们押什么？"          → 策略探索
```

**模式可切换**：随着对话推进，可以从一个问题探索过渡到方案发散。

## §1 4 模式操作手册

### 模式 1：问题探索

> 适用：PM 感知到某问题领域但没明确定义要解决什么。

**目标**：在跳进方案前，深入理解问题空间。

**必做动作**：
- 第一个问题必须是"**谁**有这个问题？"
- 第二个问题必须是"他们**现在是怎么处理的**？"
- 区分症状与根因（持续追问"为什么"直到触及结构原因）
- 探查"在不同用户分群中问题是否一致"（问题很少以同样方式影响所有人）

**必用追问**：
- "如果我们什么都不做，会发生什么？谁会受影响？怎么受影响？"
- "谁在别的语境下解决过这个问题的某个版本？"
- "这到底是认知问题、能力问题、还是动机问题？"
- "要让这个问题根本不存在，需要哪些前提成立？"

**反模式**：
- ❌ 一上来就问"你想要什么样的解决方案"——会先入为主
- ❌ 把用户描述当真理——可能是症状不是根因

### 模式 2：方案发散

> 适用：问题已定义清楚，需要生成多个可能方案。

**目标**：发散思考，先求数量再求质量。

**必做动作**：
- **评估前先出 5-7 个彼此不同的方案**
- 沿有意义的维度拉开差异：范围（小修 vs 大下注）/ 路径（产品 vs 流程 vs 政策）/ 节奏（快速见效 vs 长期投入）
- **必须包含 1 个"如果我们反过来做呢？"的选项**
- **必须包含 1 个"通过删减而不是新增"解决问题的选项**
- **抵抗过早收敛**——PM 抓住第一个还不错的想法就停下时，推动继续往下想

**5 个发散技巧**：
1. **移除约束**："如果没有技术/预算/政治约束，你会做什么？"再倒推哪些部分真正可行
2. **类比**："另一个行业是怎么解决这类问题的？能借用什么？"
3. **反转**："如果要把问题变得更糟，我们会怎么做？"——然后反过来
4. **拆解**：把问题拆成多个子问题分别求解，再组合
5. **切换用户视角**："资深用户会怎么解决？全新用户？管理员？一个讨厌我们产品的人？"

**反模式**：
- ❌ 前 3-5 个想法是所有人都能想到的，就停——继续往下想
- ❌ 在发散阶段评估可行性——会扼杀创造性

### 模式 3：假设验证

> 适用：PM 已有想法/方向，需要先检验是否站得住。

**目标**：投入执行前找出最脆弱的环节。

**必做动作**：
- 列出想法成立的**全部假设**（说出来的 + 没说的）
- 对每个假设都问"我们有多确定？有什么证据？什么情况会推翻它？"
- **找出风险最高的假设**——一旦错了就会让整个想法失效的那个
- 提出**在不真正开做之前验证最高风险假设的最低成本方式**
- 扮演反方，提出**反对这个想法的最强论据**

**6 类必查假设**：
| 类型 | 关键问题 |
|------|---------|
| 用户 | "用户想要这个"——证据来自哪里？涉及多少用户？ |
| 问题 | "这是真问题"——发生频率？用户到底有多在意？ |
| 方案 | "这方案能奏效"——为什么选这条？还有哪些替代方案被排除了？ |
| 商业 | "这会带动指标"——是哪个指标？幅度？时间周期？ |
| 可行性 | "我们能做出来"——时间范围？代价和取舍？ |
| 采纳 | "用户会发现并使用"——他们怎么发现？要他们改变什么行为？ |

**反模式**：
- ❌ 只列"我们觉得没问题"的假设
- ❌ 最高风险假设想都不想直接跳过

### 模式 4：策略探索

> 适用：思考的是方向、定位、大下注，而非某个具体功能。

**目标**：把战略空间看清楚。

**必做动作**：
- 先把可能的战略动作**摊开**——不只盯着最显眼的那一个
- 用"下注视角"思考：押的是什么、胜算如何、回报在哪里
- 考虑**二阶效应**："做 X 会因此打开什么，又会封死什么？"
- 带入**竞争动态**："这么做，竞争对手会怎么回应？"
- **时间尺度思考**："3 个月 / 12 个月 / 3 年，各自最合适的动作是什么？"

**反模式**：
- ❌ 只看"最显眼"的一个动作
- ❌ 不考虑二阶效应（"我们做了 X，竞品会怎么反击"）

## §2 4 框架工具箱

> 框架是思考工具，不是待填空模板。只有在它确实推动对话前进时才引入。

### HMW（How Might We）

把痛点改写为机会。

**结构**：`我们可以在不受 [约束] 的前提下，帮助 [用户] 实现 [期望结果]？`

**粒度判断**：
- ❌ 太宽泛："我们可以如何改进新手引导？"——什么都能往里装
- ❌ 太狭窄："我们可以如何给第 3 步加提示气泡？"——已经是方案
- ✅ 合适："我们可以如何帮助新用户在 10 分钟内获得第一次成功体验？"

**用法**：针对同一问题陈述，生成 5-10 个 HMW 问句。每一次重述都会打开不同方案空间。

### JTBD（Jobs-to-be-Done）

从用户要完成的任务出发思考，而不是从功能或人口属性出发。

**结构**：`当 [情境] 发生时，我想要 [动机]，这样就能 [期望结果]。`

**关键洞察**：
- 方案在变，任务往往稳定（几十年来人们一直在"雇用"各种方案同步进展：备忘录/邮件/Slack/共享文档）
- **功能性任务**通常更易识别
- **情绪性任务**（更有信心、显得专业）和**社会性任务**（被视为领导者）往往更有驱动力
- 关键问："他们为了选你的产品，**放弃了什么**？"——揭示真实竞争集合

### SCAMPER

7 个视角对现有产品/流程做系统化发散：

| 视角 | 问题 |
|------|------|
| **S**ubstitute（替代） | 哪个组成部分可被替换？如果这一步由另一类用户完成呢？ |
| **C**ombine（组合） | 把两个功能/工作流/用户角色合并会怎样？ |
| **A**dapt（适配） | 能借用别的产品/行业的什么做法？ |
| **M**odify（修改） | 放大 10 倍 / 缩小 10 倍 / 加快 10 倍会怎样？ |
| **P**ut to other use（挪作他用） | 这个功能能服务另一类用户/场景吗？ |
| **E**liminate（删除） | 删掉它会怎样？有人会注意到吗？ |
| **R**everse（反转） | 完全反过来？顺序颠倒？默认值倒过来？ |

### OODA（Observe–Orient–Decide–Act）

来自军事战略的**决策节奏**框架，适合快速变化、竞争激烈的环境。

```
观察（Observe）→ 定向（Orient）→ 决策（Decide）→ 行动（Act）
       ↑________________________________________|
```

**核心**：比竞争对手**更快循环**这四步。

**何时用**：
- 团队讨论过久、迟迟不动时
- 竞争动态很重要时
- 脑暴一直打转却不收敛时
- 探索策略问题时

**威力**：基于现有信息先完成定向，再决策、行动，再用下一轮观察修正方向。**循环最快的团队，学习也最快。**

## §3 5 步会话结构

> 一场好的头脑风暴是有节奏的：先打开，再收拢。

### Step 1：框定（Framing）

**目标**：在生成想法前先设定边界。

```markdown
我们这次在探索什么？（一个具体问题 / 一个机会领域 / 一个战略问题）
为什么是现在？（什么触发了这次脑暴？）
我们已经知道什么？（既有研究、数据、客户反馈）
约束条件是什么？（时间、技术、商业、团队）
这次会话如果效果好，最后会是什么样？
```

**警告**：框定不清的脑暴，产出的想法往往和真实需求连不上。

### Step 2：发散（Diverge）

**目标**：尽可能多产生想法，先不评判。

- 顺着想法往上搭，不要立刻打掉
- 跟随岔路走——最好的点子常来自意料之外的连接
- 不要停在显而易见的地方——**前 3-5 个想法通常是所有人都会想到的，继续往下想**
- 用带刺激性的提问打开新方向
- 用 §2 的框架系统化探索不同角度

### Step 3：激发（Provoke）

**目标**：挑战并延展思考。这里最能体现"交锋伙伴"的价值。

**5 类激发问题**：
- "反对这个想法的**最强论据**是什么？"
- "谁会**讨厌**这个？为什么？"
- "我们没看到的是什么？"
- "如果是某家特定公司或某个人，会怎么做得不同？"
- "如果现实恰好相反呢？"
- "它有没有一个**野心大 10 倍的版本**？"

### Step 4：收敛（Converge）

**目标**：按真正重要的维度评估，识别最值得继续追的 2-3 个想法。

- 把相关想法归并成几个主题
- 按这些维度评估：用户影响 / 可行性 / 战略一致性 / 证据强度
- **不要靠集体表决把想法消灭掉**——如果某个想法让 PM 真的兴奋，即使风险高也值得继续探索
- 对每个值得继续追的想法，**点出最大未知项 + 解决它的最低成本方式**

### Step 5：记录（Document）

**目标**：把真正重要的内容记下来。没有记录的脑暴等于没发生。

记录项：
- 关键想法 + 为什么有意思
- 需要验证的假设
- 需要进一步研究的问题
- 建议的下一步（研究/原型/访谈/写一页纸说明）
- **被明确搁置的内容**——有兴趣但不适合现在做的想法

## §4 怎么成为好的思考伙伴

| 应该 | 不应该 |
|------|--------|
| 有明确判断（"我认为方案 B 更强，因为……"） | 生硬堆框架（不是待打勾清单） |
| 建设性挑战（"这前提假设了 X——我们有把握吗？"） | 生清单甩给对方（脑暴是对话不是交付物） |
| 带来意外视角（跨行业类比、反例、边界案例） | 什么都赞同（只验证对方的不能算真伙伴） |
| 匹配对方能量（PM 对某方向兴奋时先顺着） | 过早优化（发散阶段不要评估可行性） |
| 追问下一步（"然后会发生什么？"） | 锚定第一个想法 |
| 指出模式（识别常见 PM 陷阱并直接点出来） | 把脑暴和决策混为一谈 |

## §5 常见反模式黑名单

| # | 反模式 | 表现 | 干预 |
|---|--------|------|------|
| 1 | **先想方案后补问题** | PM 还没定义问题就"我们做 X" | 慢下来，追问 X 到底解决什么、怎么知道这是真问题 |
| 2 | **功能对标陷阱** | "竞品有 X 所以我们也要 X" | 追问 X 服务的真实需求，有没有更好的满足方式 |
| 3 | **过早被约束卡住** | "技术做不了"压过发散 | 先放一边约束，自由探索，再判断可行性 |
| 4 | **单一想法式脑暴** | 带着预设方案"走过场" | 先承认它，再追问"还有什么别的方式？" |
| 5 | **分析瘫痪** | 探索很多但不收敛 | 推动一句"如果现在必须选一个方向，会选哪个？为什么？" |
| 6 | **该做研究却在脑暴** | 讨论反复打转因为没人知道答案 | 停下来，先定义还需要补哪类研究 |
| 7 | **过早被兴奋带走** | 抓住第一个"还不错"的想法就停 | 推动继续往下想，前 3-5 个想法通常所有人都能想到 |
| 8 | **评判混进发散** | 发散阶段就评估可行性 | 明确划分阶段，发散时不评判 |

## §6 与 demand-detective 的衔接

| 项 | brainstorming（本） | demand-detective |
|------|---------------------|------------------|
| 阶段 | 早期：方向还没收敛 | 中期：方向已定但规则未明 |
| 输入 | 模糊想法 / 问题空间 | 已收敛的方向 + 一句话需求 |
| 输出 | 2-3 个值得继续追的想法 | A/B 决策题 + 分级任务单 |
| 模式 | 发散 | 收敛 |
| 触发 | "想不清楚"、"一起想想" | "做个借出功能"、"做个报表" |

**典型工作流**：
1. **brainstorming**：PM 想到"我们想做个 AI 助手"，4 模式中走"方案发散"→ 收敛出 3 个方向
2. **demand-detective**：选定方向后，对每个方向用 A/B 决策题挖出关键业务决策
3. **vision-builder**：决策清单收敛后写愿景文档
4. **plan-review**：评估计划
5. **spec-writer**：写规范

## §7 健康度自检

| 指标 | 红色阈值 | 含义 |
|------|---------|------|
| 一次会话模式切换次数 | > 3 | 模式未明确定位 |
| 方案发散总数 | < 5 | 探索空间没打开 |
| 反向思考次数 | 0 | 没真正挑战既有想法 |
| 假设验证中"最高风险假设"未识别 | > 0 | 关键风险被跳过 |
| 收敛想法数 | > 5 或 < 1 | 没真正收敛 |
| "下一步建议"缺失 | > 0 | 脑暴白做 |
| 显式搁置内容 | 0 | 没真正做边界判断 |

## §8 快速使用示例

### 示例 1：早期产品探索

**输入**："我们想做一个面向开发者的 AI 编程助手。"

**模式判定**：方案发散（已有方向，需要更多方案）

**框定**：
- 探索：面向开发者的 AI 编程助手的不同形态
- 触发：竞品动作 + 用户访谈信号
- 已知：用户痛点是 Review 跟不上 Agent 产出
- 约束：3 个月内 MVP，技术栈 TS/React

**发散（8 个方向）**：
1. IDE 插件（VSCode/Cursor）
2. CLI 工具（类 Claude Code）
3. Web 平台（在线 IDE + Agent）
4. PR Review 工具（专攻 review 端）
5. 团队协作平台（多人共享 Agent）
6. 企业私有部署（合规导向）
7. **反转**：不做"助手"做"对抗者"——找代码漏洞的 AI
8. **删除**：砍掉所有 IDE 集成，只做 CLI + Web

**激发**：
- 反对 4 的最强论据：竞品 CodeRabbit/Graphite 已经占位，差异化在哪？
- 谁会讨厌 4？不写代码的 PM 觉得这是开发者的工具
- 4 的野心 10 倍版本：把整个 Code Review 流程 AI 化

**收敛**：选定 4 + 6 的组合形态

**记录**：
- 关键想法：差异化选 PR Review 端 + 企业部署
- 最大未知：企业部署的合规成本
- 下一步：访谈 5 个潜在企业客户

### 示例 2：方案假设验证

**输入**："我打算用 AI 把所有用户咨询都自动化掉。"

**模式判定**：假设验证

**必查假设**：
| 假设 | 风险等级 | 最低成本验证 |
|------|---------|------------|
| 用户愿意和 AI 聊 | 中 | 5 个用户访谈 |
| AI 能解决 80% 咨询 | 高 | 跑 100 条历史工单看 AI 答对率 |
| 自动化掉咨询能省 1 个客服成本 | 高 | 算 ROI 数字 |
| AI 出错时用户会接受 | 中 | 故意让 AI 答错，看用户反应 |
| 客服愿意被替代 | 低 | 团队 1-on-1 |

**最高风险假设**：AI 能解决 80% 咨询（**答对率不到 80% 整个项目就垮**）

**最低成本验证**：拿 100 条历史工单跑 AI 答，统计答对率
